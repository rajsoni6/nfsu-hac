SECTION 1 — PACKAGES INSTALLED
================================================================================

File: backend/package.json

The following npm packages are installed and used for MFA:

  speakeasy    — TOTP secret generation and code verification (RFC 6238)
  qrcode       — QR code image generation for authenticator app setup

These are production dependencies, not dev-only.

================================================================================
SECTION 2 — DATABASE SCHEMA — MFA FIELDS ON USER MODEL
================================================================================

File: backend/src/models/User.model.js

The User schema stores two MFA-specific fields per user account:

  mfaSecret   : { type: String, default: null }
                Stores the base32-encoded TOTP secret.
                This field is EXCLUDED from all API responses
                (authenticate.js selects '-passwordHash -mfaSecret').

  mfaEnabled  : { type: Boolean, default: false }
                Set to true only after the user successfully verifies
                their first TOTP code, confirming the authenticator app
                is correctly configured.

These fields exist on every User document regardless of role.
MFA is enforced at login for admin and coordinator roles.

SECTION 3 — MFA SETUP FLOW
================================================================================

File: backend/src/controllers/auth.controller.js
Route: POST /api/auth/mfa/setup  (authenticate middleware required)

Step 1 — Admin or coordinator calls /mfa/setup while logged in.

Code (auth.controller.js — exports.setupMfa):

  const secret = speakeasy.generateSecret({
    name: `${process.env.MFA_ISSUER}:${req.user.username}`
  });
  req.user.mfaSecret = secret.base32;
  await req.user.save();

  const qr = await qrcode.toDataURL(secret.otpauth_url);
  return success(res, { qr, secret: secret.base32 }, 'MFA secret generated.');

What this does:
  - speakeasy.generateSecret() creates a cryptographically random TOTP secret
  - The secret is stored in base32 format on the User document (mfaSecret field)
  - MFA_ISSUER from .env is used as the issuer name in the authenticator app
    (configured as: MFA_ISSUER=NFSU_Placement)
  - A QR code data URL is returned — the user scans this with Google Authenticator,
    Authy, or any RFC 6238-compatible app
  - mfaEnabled remains false until Step 2 is completed

Step 2 — User scans QR code and submits the 6-digit code to confirm setup.

Route: POST /api/auth/mfa/enable  (authenticate middleware required)

Code (auth.controller.js — exports.enableMfa):

  const verified = speakeasy.totp.verify({
    secret: user.mfaSecret,
    encoding: 'base32',
    token,       // 6-digit code from authenticator app
    window: 1,   // allows ±1 time step (30-second tolerance)
  });

  if (!verified) return error(res, 'Invalid token', 401);

  user.mfaEnabled = true;
  await user.save();
  await logAudit(user._id, AUDIT_ACTIONS.MFA_ENABLED, req);

What this does:
  - Verifies the submitted 6-digit code against the stored secret
  - window: 1 allows a ±30-second clock drift tolerance
  - Only sets mfaEnabled = true if the code is correct
  - Writes MFA_ENABLED to the AuditLog (tamper-evident record)
  - If the code is wrong, mfaEnabled stays false and HTTP 401 is returned

SECTION 4 — MFA LOGIN FLOW
================================================================================

File: backend/src/controllers/auth.controller.js
Route: POST /api/auth/login

Step 1 — User submits username + password.

Code (auth.controller.js — exports.login):

  // MFA required for admin and coordinator
  if (user.mfaEnabled && ['admin', 'coordinator'].includes(user.role)) {
    user.lastLogin = new Date();
    await user.save();
    const tempToken = jwt.sign(
      { username: user.username },
      process.env.JWT_ACCESS_SECRET,
      { expiresIn: '5m' }
    );
    return success(res, { mfaRequired: true, tempToken }, 'MFA verification required');
  }

What this does:
  - Password is verified first (bcrypt.compare)
  - If the user has mfaEnabled = true AND is admin or coordinator:
      → No access token is issued yet
      → A short-lived tempToken (5 minutes) is returned
      → tempToken contains only { username } — no role or permissions
      → The client is told mfaRequired: true
  - The user cannot access any protected route with tempToken
    (it does not carry id or role, so authenticate.js will reject it)

Step 2 — User submits the 6-digit TOTP code.

Route: POST /api/auth/mfa/verify

Code (auth.controller.js — exports.verifyMfa):

  // Verify tempToken to get username
  const decoded = jwt.verify(tempToken, process.env.JWT_ACCESS_SECRET);
  username = decoded.username;

  const user = await User.findOne({ username });
  if (!user || !user.mfaSecret) return error(res, 'Invalid request', 400);

  const verified = speakeasy.totp.verify({
    secret: user.mfaSecret,
    encoding: 'base32',
    token,     // 6-digit code from authenticator app
    window: 1,
  });

  if (!verified) return error(res, 'Invalid MFA token', 401);

  const accessToken = signAccess(user._id, user.role);
  const refreshToken = signRefresh(user._id);
  // ... set cookie, return tokens

What this does:
  - Validates the tempToken signature and expiry (5-minute window)
  - Looks up the user by username from the tempToken
  - Verifies the 6-digit TOTP code against the stored mfaSecret
  - Only on success: issues the full access token (15 min) and refresh token (7 days)
  - If tempToken is expired or tampered → HTTP 401
  - If TOTP code is wrong → HTTP 401, no tokens issued

SECTION 5 — INPUT VALIDATION FOR MFA ENDPOINTS
================================================================================

File: backend/src/validators/auth.validator.js

The MFA verify endpoint validates its input with Joi before reaching the controller:

  const mfaVerifySchema = Joi.object({
    username: Joi.string().trim().lowercase().required(),
    token:    Joi.string().length(6).pattern(/^\d+$/).required(),
  });

  - token must be exactly 6 characters
  - token must be all digits
  - Any other format returns HTTP 422 before the controller runs

File: backend/src/routes/auth.routes.js

  router.post('/login',      authLimiter, validateLogin,     ctrl.login);
  router.post('/mfa/verify', authLimiter, validateMfaVerify, ctrl.verifyMfa);
  router.post('/mfa/setup',  authenticate,                   ctrl.setupMfa);
  router.post('/mfa/enable', authenticate,                   ctrl.enableMfa);

  - authLimiter: 10 requests / 15 minutes per IP (brute-force protection)
  - authenticate: JWT required — setup and enable only available when logged in

SECTION 6 — MFA SECRET PROTECTION
================================================================================

File: backend/src/middleware/authenticate.js

  const user = await User.findById(decoded.id).select('-passwordHash -mfaSecret');

The mfaSecret field is explicitly excluded from every authenticated request.
It is never present in req.user and never returned in any API response.

File: backend/src/models/User.model.js — toSafeObject()

  delete obj.mfaSecret;

Even if toSafeObject() is called, mfaSecret is deleted before the object
is returned to the client.

SECTION 7 — AUDIT TRAIL FOR MFA EVENTS
================================================================================

File: backend/src/utils/constants.js

  AUDIT_ACTIONS = {
    ...
    MFA_ENABLED: 'MFA_ENABLED',
    ...
  }

File: backend/src/controllers/auth.controller.js — exports.enableMfa

  await logAudit(user._id, AUDIT_ACTIONS.MFA_ENABLED, req);

Every time MFA is successfully enabled on an account, an AuditLog document
is created with:
  - actor: the user's _id
  - action: 'MFA_ENABLED'
  - ipAddress: client IP
  - userAgent: client browser string
  - timestamp: exact time of enablement

This record is append-only and cannot be modified or deleted.

SECTION 8 — FRONTEND MFA CHALLENGE (LOGIN PAGE)
================================================================================

File: frontend/index.html

The login page implements a two-step UI:

Step 1 — Credentials form (id="step-login"):
  Submits username + password to POST /api/auth/login

  if (res.data.mfaRequired) {
    pendingUser = res.data.tempToken;
    document.getElementById('step-login').style.display = 'none';
    document.getElementById('step-mfa').style.display = 'block';
    return;
  }

  If mfaRequired is true, the credentials form is hidden and the MFA
  challenge form is shown. The tempToken is held in memory (not localStorage).

Step 2 — MFA challenge form (id="step-mfa"):
  Submits tempToken + 6-digit code to POST /api/auth/mfa/verify

  body: JSON.stringify({
    token: document.getElementById('mfa-code').value,
    tempToken: pendingUser
  })

  On success: accessToken and user object stored, redirect to dashboard.
  On failure: error message shown, user stays on MFA step.

  Input field constraints:
    maxlength="6"
    inputmode="numeric"
    pattern="\d{6}"
